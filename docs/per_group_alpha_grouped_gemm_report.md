# Per-Group Alpha (Scaling) Is Ignored in the Xe Grouped GEMM Epilogue

**Component:** `sgemm_lora_b_fwd` (and any grouped GEMM that needs a different
scalar `alpha` per group) on Intel BMG (Battlemage) via CUTLASS-SYCL / sycl-tla.

**Status:** Root cause found and *proven* with a minimal reproducer. Fix
identified. Fix not yet landed in our code (this report precedes the change).

**TL;DR:** In a grouped GEMM, each group is supposed to compute
`D = alpha[group] * (A @ B) + beta * C`. On the Intel Xe grouped epilogue, the
per-group `alpha` is silently ignored — **every group uses `alpha[0]`**. The
cause is that the grouped kernel hard-codes the batch/group coordinate (the "L"
coordinate) to `0` when it calls the epilogue, and the fusion code reads
`alpha` as `alpha_ptr_array[L_coord]` — i.e. always `alpha_ptr_array[0]`. The
fix is to select the correct per-group `alpha` pointer *before* the epilogue
runs, in the one place the grouped epilogue already selects per-group `C`/`D`
pointers. Because that place lives in a **custom collective epilogue** we own,
this does not require patching the fetched CUTLASS/sycl-tla source.

---

## 0. Background for readers new to CUTLASS (read this first)

You do not need CUTLASS experience to follow this. A few terms:

- **GEMM**: a matrix multiply `D = alpha * (A @ B) + beta * C`. `alpha` and
  `beta` are scalars. `C` is an optional matrix added on top (the "residual").
- **Grouped GEMM**: many independent GEMMs of *different shapes* run in one
  kernel launch. Each independent problem is a **group**. Group `g` has its own
  `A_g`, `B_g`, `C_g`, `D_g`, and can have its own `alpha_g` / `beta_g`.
  In our LoRA-B kernel, one "group" = one segment of tokens that share a LoRA
  adapter, and `alpha_g` = that adapter's `scaling` (`lora_alpha / rank`).
- **Epilogue**: the final stage of a GEMM. After the matrix product `A @ B` is
  accumulated, the epilogue applies `alpha`, adds `beta * C`, converts the
  datatype, and writes `D`. "Per-group alpha" is entirely an epilogue concern.
- **Fusion callbacks**: CUTLASS's modular epilogue system. `LinearCombination`
  (`alpha*acc + beta*C`) is expressed as small composable nodes. The node that
  produces the `alpha` scalar is `Sm90ScalarBroadcastPtrArray`.
- **The "L" coordinate (a.k.a. batch/group index)**: CUTLASS addresses tensors
  with a coordinate `(m, n, k, l)`. The `l` axis is the batch dimension. In a
  grouped GEMM the framework carries the current group through this `l`
  coordinate in some code paths — **and this is exactly where the bug is.**
- **`alpha_ptr_array`**: a device array holding one `float*` per group, so the
  epilogue can fetch a *different* alpha per group by indexing with `l`.

### Where the code physically lives — and the sycl-tla surprise

The CUTLASS-SYCL headers we compile against are **fetched at build time** into:

```
build/_deps/repo-cutlass-sycl-src/
```

That directory is **not CUTLASS from NVIDIA** and it is **not a vendored copy we
maintain**. Our `CMakeLists.txt` pulls it directly:

```cmake
# sgl-kernel-xpu-upstream/CMakeLists.txt (~line 81)
FetchContent_Declare(
    repo-cutlass-sycl
    GIT_REPOSITORY https://github.com/intel/sycl-tla.git   # <-- THIS is sycl-tla
    ...)
```

> **Answering the "did we touch sycl-tla?" doubt directly:**
> **`repo-cutlass-sycl-src` *is* sycl-tla.** "CUTLASS-SYCL" and "sycl-tla" are
> two names for the same Intel repository (`intel/sycl-tla`, currently at
> `v0.9.1-15-g525faea3`). So when I edited a header under
> `build/_deps/repo-cutlass-sycl-src/...` to prove the fix, I *was* editing
> sycl-tla. That edit is a **throwaway experiment**: `build/_deps/` is
> regenerated by CMake and is not under our version control. **The real fix must
> live in code we own** (`src/sycl/kernels/lora/...`), and then the sycl-tla
> edit gets reverted. That is the entire reason a custom collective epilogue is
> needed — see §6.

## 1. Symptom

`sgemm_lora_b_fwd` computes, per token-segment `s`:

```
output[s] = scalings[lora(s)] * (input_x[s] @ weights[lora(s)]^T) + base_output[s]
```

`scalings[lora(s)]` is the per-segment `alpha`. With multiple segments that use
*different* adapters (hence different scalings), the result is wrong: every
segment is scaled by the **first** segment's scaling instead of its own. The
`+ base_output` residual (the `beta * C` term) is correct — only per-group
`alpha` is broken.

---

## 2. How the issue was found

The investigation used the upstream example `examples/04_bmg_grouped_gemm`,
which exercises the exact same grouped-GEMM machinery our kernel uses.

1. **Built the stock example** for BMG and ran it — it "Passed", which was
   misleading (see step 3).

2. **Built a controlled reproducer** (`bmg_grouped_gemm_pergroup_alpha.cpp`,
   committed alongside this report's investigation) with 3 groups, tiny 8×8×8
   matrices, `A = B = [1,2,3,...]`, `C = all ones`, and
   **alpha = [10, 50, 100]**. Expected per-group outputs are then trivially
   `10*X+1`, `50*X+1`, `100*X+1` for the same base product `X`. If all three
   groups print the *same* number, per-group alpha is being ignored.

3. **Discovered the stock example never tested the per-group path.** The
   example only takes the per-group (`alpha_ptr_array`) branch when
   `alpha == beta == FLT_MAX`, but its CLI parser defaults them to `1.f`/`0.f`,
   so the per-group branch is effectively dead and the "Passed" result only
   proved the *scalar* path works. The reproducer forces the per-group branch
   unconditionally.

4. **Ran the reproducer → all three groups produced `alpha[0]`'s result.**
   Per-group alpha confirmed ignored.

5. **Traced the data flow** from the fusion `alpha` read back to the kernel:
   - `Sm90ScalarBroadcastPtrArray::update_scalar()` reads
     `scalar = *(scalar_ptr_arrays[0][l_coord])`
     (`include/cutlass/epilogue/fusion/sm90_visitor_load_tma_warpspecialized.hpp`).
     So the group is selected by `l_coord`.
   - The epilogue's `l_coord` comes from the tile coordinate handed in by the
     grouped kernel: `xe_gemm_array_cooperative.hpp:288`
     `auto tile_coord = make_coord(m_coord, n_coord, _, 0);` — **the L slot is
     hard-coded to `0`.** That coordinate is passed straight into the epilogue
     at line 320. So every group reads `alpha_ptr_array[0]`.
   - The kernel *does* know the real group: `curr_group = work_tile_info.L_idx`
     (line 259), and it already uses `curr_group` to pick this group's `C`/`D`
     base pointers via `to_base_arguments(params.epilogue, curr_group)`
     (line 284). It just never propagates the group into the epilogue's tile
     coordinate.

6. **Proved the fix** by offsetting the alpha pointer array by the group index
   in `to_base_arguments` (see §5), rebuilding, and re-running:

   | Group | alpha | Output (col 0) | Expected (`alpha*1380 + 1`) |
   |------:|------:|---------------:|----------------------------:|
   | 0     | 10    | **13801**      | 13801 ✓ |
   | 1     | 50    | **69001**      | 69001 ✓ |
   | 2     | 100   | **138001**     | 138001 ✓ |

   **Disposition: Passed**, with the `+1` residual intact and each group scaled
   by its own alpha.

### A false alarm worth recording

An earlier version of the reproducer pushed **beta** through `beta_ptr_array`
(the array path) as well, and the `beta * C` residual disappeared (output was
exactly `alpha*(A@B)`, no `+1`). That looked like a *second* bug. It is **not a
problem for us**: our kernel never uses `beta_ptr_array` — `beta` is a plain
scalar (`args_from_options` sets `fusion_args.beta = beta`, `beta_ptr_array =
nullptr`). Re-running the reproducer with the kernel's *exact* config
(per-group `alpha_ptr_array` + **scalar** `beta = 1`) gives the correct `+1`.
The scalar-beta path was independently confirmed on the stock example with
`--beta=1` and `--beta=3` (both Passed). **Conclusion: there is only one bug —
per-group alpha — and the residual add works fine on the config we ship.**

## 3. Root cause (precise)

```
Kernel: build/_deps/repo-cutlass-sycl-src/include/cutlass/gemm/kernel/xe_gemm_array_cooperative.hpp

  259:  curr_group = work_tile_info.L_idx;                       // kernel KNOWS the group
  284:  ...to_base_arguments(params.epilogue, curr_group)...     // per-group C/D pointers selected here
  288:  auto tile_coord = make_coord(m_coord, n_coord, _, 0);    // <-- L coordinate HARD-CODED to 0
  320:  epilogue(problem_shape_MNKL, subgroup_shape, tile_coord, // tile_coord (L=0) handed to epilogue
           accumulators, tiled_mma, thread_idx);

Fusion: include/cutlass/epilogue/fusion/sm90_visitor_load_tma_warpspecialized.hpp
  Sm90ScalarBroadcastPtrArray::update_scalar():
    scalar = *(params_ptr->scalar_ptr_arrays[0][l_coord]);       // l_coord is always 0
```

Because the grouped kernel passes each group as a *separate problem with L = 1*
and pre-selects that group's `C`/`D` pointers (the `[idx]` indexing in
`to_base_arguments`), the tile's L coordinate is *intentionally* `0` for the
tensor addressing to be correct. But the fusion's `alpha_ptr_array` lookup piggy-
backs on that same `l_coord`, so it can never see anything but index `0`.

In short: **C/D are made per-group by pre-offsetting their base pointers; alpha
is *not*, so it stays stuck at group 0.**

---

## 4. Why the natural-looking alternatives don't work

- **"Just set `dAlpha` L-stride and let `l_coord` index it."** That is what our
  runner already does (`dAlpha = {_0,_0,1}`, one pointer per segment). It fails
  because `l_coord` is hard-coded to `0` upstream (§3), so the stride is
  multiplied by `0`.
- **"Feed the real group as the L coordinate at line 288."** That would fix
  alpha but *break* `C`/`D` addressing, because those pointers are already
  pre-offset per group under the assumption `L == 0`. You'd be applying the
  group offset twice. (It also requires editing the fetched sycl-tla kernel,
  which we don't own — see §0/§6.)
- **"Use `beta_ptr_array` for the residual too."** Unnecessary and, on this Xe
  epilogue, currently mishandled (§2 false alarm). Scalar beta already works.

The only correct-and-owned lever is to **pre-offset the alpha/beta pointer
array by the group index in the same place C/D are already pre-offset** — i.e.
mirror exactly what already works for C/D.

---

## 5. The fix (what it does)

In the grouped collective epilogue's `to_base_arguments(args, idx)` — the
function the kernel calls once per group with `idx == curr_group` — advance the
alpha (and beta) pointer arrays by `idx`, so index `[0]` inside the fusion
resolves to *this group's* alpha:

```cpp
CUTLASS_DEVICE static constexpr BaseArguments
to_base_arguments(Arguments const &args, int idx) {
  // C/D base pointers are already selected per group via [idx]. The grouped
  // kernel passes L=1 with tile_coord L==0, so the fusion always reads
  // alpha_ptr_array[0]. Offset the alpha/beta pointer arrays by the group
  // index here so each group picks up its own scalar -- mirroring the C/D
  // indexing. l_coord stays 0, so C/D addressing is unaffected.
  auto thread = args.thread;
  if (thread.alpha_ptr_array != nullptr) { thread.alpha_ptr_array += idx; }
  if (thread.beta_ptr_array  != nullptr) { thread.beta_ptr_array  += idx; }
  return BaseArguments{ thread, args.ptr_C[idx], args.dC[idx],
                        args.ptr_D[idx], args.dD[idx]};
}
```

This is the identical trick already used for `C`/`D` (`args.ptr_C[idx]` etc.),
extended to the scalar pointer arrays.

### Is the fix efficient? (your specific question)

**Yes — it is effectively free.**

- `to_base_arguments` runs **once per group**, not per tile, per subgroup, or
  per element. The kernel guards it behind `if (did_group_change)`
  (`xe_gemm_array_cooperative.hpp:279`, reset at line 331), so it fires only
  when the scheduler moves to a new group.
- The added work is **one pointer addition** (`ptr += idx`) per array, per
  group. No new memory traffic, no extra kernel launches, no change to the
  compute-bound MMA loop or the per-element epilogue math.
- The value read is the same size (`fp32`) from the same array; we only change
  *which element* is read — and we make it read the correct one.
- It removes no fusion nodes and changes no datatypes, so codegen/register
  pressure is unchanged.

Net: same asymptotic cost, one extra integer add per group. Correctness win at
zero measurable performance cost.

## 6. Why we need a *custom collective epilogue* (and not a sycl-tla patch)

The fix lives in `to_base_arguments`, which is a method of the grouped
**collective epilogue** class:

```
build/_deps/repo-cutlass-sycl-src/include/cutlass/epilogue/collective/xe_array_epilogue.hpp
  CollectiveEpilogue<IntelXeGenericGroup, ...>::to_base_arguments(...)
```

That file is part of **sycl-tla**, fetched into `build/_deps/` by CMake (§0).
Editing it directly is not acceptable for shipping because:

1. **`build/_deps/` is regenerated.** A clean build, a CMake cache wipe, or a
   sycl-tla version bump silently discards the edit. The bug would reappear with
   no trace.
2. **We don't own that repo.** It's `intel/sycl-tla` upstream. We can't merge
   into our tree, can't code-review it there on our schedule, and can't
   guarantee the pin.
3. **Our kernel already defines its own epilogue types** in
   `src/sycl/kernels/lora/common/group_gemm_types.hpp` (the
   `CollectiveEpilogue<IntelXeGenericGroup, ...>` alias). That is the seam where
   we can substitute a subclass/replacement whose `to_base_arguments` carries
   the offset — **in code we own, that survives rebuilds.**

So the plan is:

- **(a)** Add a small custom collective epilogue in `src/sycl/kernels/lora/`
  that derives from / mirrors the `IntelXeGenericGroup` collective epilogue and
  overrides `to_base_arguments` with the `+= idx` offset shown in §5.
- **(b)** Point `group_gemm_types.hpp`'s `CollectiveEpilogue` alias at our
  version.
- **(c)** **Revert** the throwaway edit in
  `build/_deps/.../xe_array_epilogue.hpp` so the fetched sycl-tla source is
  pristine again.

The upstream sycl-tla kernel bug (L hard-coded to 0 at
`xe_gemm_array_cooperative.hpp:288`) should also be reported to Intel so it can
be fixed at the source; our custom epilogue is the local workaround until then.
